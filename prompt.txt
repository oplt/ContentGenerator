PHASE 1 — DURABLE NODE EXECUTION AND ATOMIC CLAIMING
====================================================

This is the highest-priority architectural gap.

Current workflow execution still performs multiple ready nodes inside `WorkflowEngine.advance()`.

Change the responsibilities to:

WorkflowEngine
= orchestration/state transitions

Celery worker
= executes one claimed WorkflowNodeRun

PostgreSQL
= authoritative execution state

Target flow:

WorkflowRun
↓
discover READY node
↓
atomically claim WorkflowNodeRun
↓
enqueue node execution
↓
Celery worker executes ONE node
↓
persist result
↓
engine determines newly ready nodes
↓
enqueue next nodes

Do not execute arbitrary expensive domain nodes inside the API process.

### 1.1 Add atomic node claims

Extend WorkflowNodeRun with fields such as:

claim_token
claim_expires_at
claimed_at
worker_task_id
next_attempt_at
last_heartbeat_at
execution_key

Use naming consistent with existing publishing claim semantics where possible.

Implement repository operations conceptually like:

claim_ready_node(...)
renew_node_claim(...)
release_node_claim(...)
complete_node(...)
fail_node(...)

Claim using PostgreSQL transaction semantics.

Prefer:

SELECT ... FOR UPDATE SKIP LOCKED

or an equivalent atomic conditional UPDATE.

Two workers must never successfully claim the same logical execution simultaneously.

### 1.2 Introduce one-node execution task

Add something equivalent to:

execute_workflow_node_task(
tenant_id,
workflow_run_id,
node_run_id,
claim_token,
)

This task executes exactly one node run.

Do not let it execute the rest of the DAG synchronously.

On successful completion:

persist result
→ unlock downstream state
→ enqueue newly-ready nodes

### 1.3 Connect TaskExecution properly

WorkflowNodeRun currently has TaskExecution linkage fields.

Actually populate them.

Model:

WorkflowRun
↓
WorkflowNodeRun
↓
TaskExecution

TaskExecution remains worker/infrastructure telemetry.

WorkflowNodeRun remains business workflow state.

### 1.4 Crash recovery

A worker can die after marking a node RUNNING.

The system must recover.

Implement a periodic recovery task:

find RUNNING nodes
where claim_expires_at < now()

Then either:

* requeue when retryable,
* or mark failed after max attempts.

Never leave RUNNING nodes permanently orphaned.

### Acceptance criteria

* Two concurrent `advance` requests cannot execute the same node twice.
* Worker crash does not permanently strand WorkflowNodeRun.
* API server does not execute video/LLM/publishing work inline.
* WorkflowRun remains recoverable after process restart.
* TaskExecution is connected to node execution.
* concurrency regression tests pass.

EXECUTION INSTRUCTION
=====================

Start with Phase 0 and Phase 1 only.

Before changing code:

1. inspect the current latest repository state;
2. compare these requirements against the actual implementation;
3. confirm which gaps still exist;
4. produce the Phase 0/1 file-level plan;
5. implement them;
6. add regression tests;
7. run the relevant quality gates.

Do not proceed to Phase 2 until Phase 0 and Phase 1 are demonstrably green.

At the end of each phase report:

* changed files,
* migrations,
* architectural decisions,
* tests added,
* commands executed,
* test results,
* backward compatibility,
* remaining gaps,
* exact next phase.
