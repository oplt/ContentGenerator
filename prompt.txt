# 4. BACKEND PERFORMANCE AND CONCURRENCY AUDIT

Determine where the application is:

* I/O-bound
* CPU-bound
* database-bound
* external-API-bound
* queue-bound

Then recommend the appropriate mechanism.

Do **not** blindly convert everything to async.

Use these principles:

### asyncio

Use `asyncio` only when several independent I/O operations can actually overlap.

Look for candidates such as:

* multiple independent HTTP API calls
* independent provider calls
* source fetching
* account-specific publishing calls
* independent metadata lookups

Where appropriate consider:

`asyncio.gather(...)`

or structured bounded concurrency.

But require:

* bounded concurrency
* timeout handling
* partial-failure semantics
* rate-limit handling
* cancellation behavior

Do not run mutually dependent work concurrently.

### Threads

Recommend threads only for genuinely blocking I/O libraries that cannot reasonably be replaced with async implementations.

Do not use threads as a generic performance solution.

### CPU-bound workloads

Investigate:

* FFmpeg/video work
* image manipulation
* large parsing jobs
* expensive scoring
* CPU-heavy transformations

Do not run expensive CPU work on the FastAPI event loop.

Prefer existing worker infrastructure such as Celery or appropriate process-based execution where warranted.

### Celery

Audit:

* task granularity
* retries
* retry backoff/jitter
* idempotency
* duplicate execution
* task acknowledgement
* transaction interaction
* timeout configuration
* worker concurrency
* queue separation
* long-running jobs
* job progress/status
* serialization overhead

Inspect especially:

* `backend/workers/celery_app.py`
* `backend/workers/tasks.py`
* `backend/workers/runtime.py`

# 6. DATABASE TRANSACTION CORRECTNESS AND PERFORMANCE

Perform a dedicated SQLAlchemy/PostgreSQL audit.

Inspect at minimum:

* `backend/db/session.py`
* `backend/db/base.py`
* `backend/db/model_registry.py`
* module `models.py`
* module `repository.py`
* module `service.py`
* Alembic migrations

For important write workflows map:

`API/worker → service → repository → session → commit/rollback`

Analyze transaction **precision**, meaning:

* atomicity
* transaction ownership
* transaction scope
* correct rollback behavior
* isolation from unrelated operations
* preventing partial updates
* preventing duplicate writes
* preventing lost updates
* preventing double publishing
* avoiding commits deep inside lower-level repositories when a service should own the unit of work

Identify misuse of:

* `commit`
* `flush`
* `refresh`
* nested transactions
* repeated transactions
* long-running transactions

Investigate whether contested state changes need:

* unique constraints
* idempotency keys
* atomic conditional updates
* optimistic concurrency/version columns
* `SELECT ... FOR UPDATE`
* PostgreSQL `ON CONFLICT`
* advisory locks

Only recommend locking when there is an actual concurrency requirement.

## Query performance

Inspect for:

* N+1 queries
* missing eager loading
* unnecessary joins
* repeated scalar queries
* row-by-row inserts/updates
* missing batch operations
* unnecessary full-table scans
* inefficient `COUNT`
* poor pagination
* offset pagination on large tables where keyset pagination would help
* inappropriate loading of full ORM objects
* repeated `refresh`
* non-selective filters

Inspect indexes against real access patterns.

For every index recommendation identify:

* table
* columns
* query pattern
* whether single-column or composite
* ordering where relevant
* uniqueness where relevant

Do not recommend indexes without identifying the query they accelerate.

Where practical use PostgreSQL `EXPLAIN` / `EXPLAIN ANALYZE` safely.

Also inspect:

* connection pool configuration
* pool exhaustion risk
* connection lifetime
* session-per-request behavior
* worker DB usage
* long transactions

# 18. FORMAT FOR EVERY ROADMAP TASK

**Problem / Evidence**
Explain the actual problem.

Include exact evidence.

**Root Cause**
Explain why it occurs.

**Best Solution**
Describe the recommended implementation.

Do not provide vague advice such as "optimize database".

Specify the design.

**Why This Solution**
Explain why this approach is preferable.

**Alternatives Considered**
Mention meaningful alternatives and why they are weaker where relevant.

**Related Files and Symbols**
Use exact paths and actual symbol names.

Example format:

* `backend/.../service.py`

  * `SomeService`
  * `some_method()`
* `backend/.../repository.py`

  * `SomeRepository.list_items()`
* `frontend/src/...`

  * `SomePage`
  * `useSomeFeature()`

Never invent symbols.

If you have not opened the file and verified the symbol, do not name it.

**Implementation Steps**
Use concrete ordered substeps.

**Database / API / UI Impact**
Describe applicable schema, migration, endpoint, frontend, or compatibility effects.

**Acceptance Criteria**
Make acceptance criteria measurable.

Examples:

* query count decreases from N+1 to <=3 queries;
* duplicate publishing is impossible for the same idempotency key;
* p95 endpoint latency improves against the established baseline;
* cache hit ratio is observable;
* page no longer performs duplicate requests;
* selected social account ID is persisted through content → publication → analytics;
* handwritten file is decomposed while behavior remains covered by tests.

Do not invent arbitrary percentage goals without a measured baseline.

**Tests / Benchmarks**
State exact test areas/files that should be added or modified.

**Dependencies**
Reference other roadmap task IDs.

**Rollback / Migration Risk**
Explain when applicable.

# 21. PERFORMANCE RECOMMENDATION RULES

Every performance recommendation must answer:

1. What is slow?
2. Where is it slow?
3. Why is it slow?
4. What evidence supports that?
5. What is the proposed fix?
6. Why is that fix appropriate?
7. How will we measure improvement?
8. What new failure modes could it introduce?

Do not recommend:

* asyncio merely because code is Python;
* threads merely because work is slow;
* Redis merely because caching is possible;
* indexes on every queried column;
* React memoization everywhere;
* microservices merely because modules are large.

Preserve the modular-monolith architecture unless strong measured evidence proves a service boundary is justified.

Prefer improving boundaries inside the existing architecture first.

# 22. SPECIAL RULES FOR EXTERNAL API / SOCIAL PROVIDER PERFORMANCE

Provider calls should be reviewed for:

* persistent HTTP clients / connection pooling
* DNS/TLS connection reuse
* timeout values
* retries
* retry-after handling
* rate limiting
* concurrency limits
* request batching where provider APIs allow it
* pagination
* duplicate calls
* response caching where safe
* error normalization

For social publishing:

* never retry unsafe publish calls without idempotency analysis;
* prevent duplicate posts;
* persist provider publication IDs;
* distinguish transient vs permanent failures;
* scope provider rate limits by account where appropriate.

# 23. CODE SIMPLIFICATION RULES

When proposing refactoring, prefer:

* smaller cohesive functions
* clear responsibility boundaries
* composition
* explicit domain models
* shared reusable primitives
* typed contracts
* simple control flow

Avoid:

* overengineering
* new abstraction layers with only one trivial use
* unnecessary design patterns
* unnecessary dependency injection frameworks
* unnecessary microservices
* unnecessary generic repositories
* code golf

A refactor must improve at least one of:

* correctness
* performance
* testability
* readability
* separation of concerns
* reuse
* maintainability

while preserving behavior.
